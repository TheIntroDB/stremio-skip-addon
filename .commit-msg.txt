refactor: hardcode the API endpoints and require the API key

Two things that should not have been knobs:

- The TheIntroDB API host and the site URL were `wrangler.jsonc` vars. There is
  one TheIntroDB API and this is its addon, so they are now constants in
  `src/constants.ts` (with the API version beside them): nothing in the
  environment can point the addon at a host it was not written for. The
  end-to-end suite stands in front of `fetch` to answer the API deterministically
  instead of overriding a binding, so `src/` keeps no test hook.

- The API key was optional and defaulted to an anonymous lookup. Anonymous
  lookups are rate limited per IP, and every Cloudflare Worker shares Cloudflare's
  egress addresses, so an anonymous deployment is limited by other people's
  traffic and would look like an addon that silently never cuts anything. The key
  is now required: `wrangler.jsonc` declares no vars at all, the Deploy to
  Cloudflare flow asks for `TIDB_API_KEY` (declared in package.json and
  .dev.vars.example), and without a key the Worker does no lookups, answers
  `403 missing_api_key` with instructions, reports `apiKeyConfigured: false` on
  /health, and the configuration page refuses to build an install link.

Also fixes the stream labels while in here: the addon used to overwrite `name`
with its own label, which threw away the quality tag a source addon puts there
(Torrentio's "4k"). The upstream `name` and `title` are now left alone, the
addon marks itself by suffixing `name` and the cut list goes on `description`,
which nothing else depends on. Streams whose source declares request headers are
not relayed at all, since this Worker does not carry them.

Tests: 58 (56 offline + 2 that need TIDB_LIVE=1 and a key). The live test now
asserts the keyed path end to end against api.theintrodb.org, and the suite
covers the missing-key refusal and the config-supplied key.
